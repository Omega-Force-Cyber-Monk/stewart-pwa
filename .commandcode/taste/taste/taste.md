# Taste
- Prefers an audit/assessment of the existing codebase before starting new feature work, so new work (e.g., API integrations) builds on a known baseline. Confidence: 0.8
- Prefers to hand off work in staged, sequential prompts (e.g., "audit now, I'll give you the API integration prompt later") rather than dumping the full scope upfront. Confidence: 0.8
- Communicates in terse, high-level directives (e.g., "okay do it", "fix all of it", "make this page fluid responsive based on industry best practices", "bring the payment functionality from standard page") and expects the assistant to infer and execute the complete scope — including adjacent issues like missing dependencies, build blockers, and security vulnerabilities — without itemizing or asking for per-item confirmation. Confidence: 0.95
- Provides authoritative, detailed specification documents (e.g., full API integration guides with endpoints, response shapes, TypeScript types, constants, tag-invalidation rules, and recommended patterns) and expects the assistant to implement faithfully against them as the source of truth, following the project's existing codebase patterns where they already implement the guide's recommendations. Confidence: 0.8
- Requires sweet-alert-style modal dialogs for all confirmations, approvals, and alerts — never native browser dialogs (`window.confirm`/`window.alert`). Confidence: 0.95
- Wants backend validation/API error messages surfaced to the user exactly as returned (including array-shaped `{ message: string[] }` responses), not generic fallback messages. Confidence: 0.95
- Reports bugs tersely (often a single symptom sentence, e.g., "the payment modal comes and disappear", "i logged in as unpaid user and it redirect me to standard page the payment modal opens and disappear", and short-viewport symptoms like "i guess hero section cut off it's content below side on my laptop", sometimes with pasted evidence like API response payloads/endpoints), expecting the assistant to diagnose the root cause and fix it without asking clarifying questions. Confidence: 0.92
- Treats UI state that opens and then silently closes itself (e.g., a payment modal that "opens and disappears" because a background async profile sync flips a derived status check) as a bug — once user-visible state like a modal is opened (via explicit click or a redirect flag), it should stay open until the user explicitly dismisses it or completes the flow. Confidence: 0.85
- Expects saved changes to persist and display correctly after a page reload — treats stale local snapshots (store/localStorage from login time) shadowing fresh server data as bugs, and expects the client to treat the server response as source of truth and sync the store after mutations. Confidence: 0.9
- Expects end-to-end data consistency after mutations: after a successful payment, subsequent API reads (e.g., the dashboard's `purchase.status`) must reflect the new paid state — treats server responses that still show pre-payment state (e.g., `purchase.status: null`) as a bug to diagnose at the root cause, client or server side. Confidence: 0.7
- After login, admins should land on the admin dashboard and riders on their own flow — not a single shared redirect for everyone. Confidence: 0.9
- Supplies exact-wording copy/content revision lists (e.g., the Women-Focused, Drivers 50+, and main selling page revisions: precise replacement phrases, FAQ answers, section copy) and expects every item applied verbatim with terminology kept consistent across the whole app (e.g., "Women-Focused" hyphenated everywhere), while leaving design/visuals unchanged unless explicitly told otherwise — the spec explicitly enumerates "keep as-is" items to prevent scope creep. Confidence: 0.95
- Expects pages to be made fluid-responsive per industry best practices when asked: fluid type via `clamp()`, `min-w-0` to prevent grid/flex overflow, aspect-ratio + `object-cover` images instead of fixed heights, `text-balance`/`text-pretty` wrapping, adequate mobile tap targets (min ~44–56px), proper mobile stacking (e.g., hero trust card stacks below content and never covers imagery), lazy-loaded below-the-fold images, and accessible nav toggles (`aria-expanded`) — all without changing the existing design, colors, or positioning. Also treats a horizontal scrollbar at any viewport width (e.g., visible on laptop) as a defect — pages must fit the viewport fluidly with no horizontal overflow. Confidence: 0.85
- Wants page-specific features to mirror an existing reference page (e.g., "add dropdown menu similar like standard page in the women page", "bring the navbar and payment button functionality from women page") — expects the same shared components, auth state/logic, and mobile-menu behavior used on the reference page to be reused wholesale for cross-page consistency, not bespoke reimplementations. Confidence: 0.95
- Wants the full auth/checkout contract replicated across every funnel/marketing page, not just a button: auth-aware navbar (ProfileDropdown when logged in, Login link + CTA when logged out), auth-aware mobile menu overlay, pricing modal wired with `?showPricing=true` auto-open (lazy-init state + URL param cleared), and a three-state footer CTA (active → dashboard link, logged-in unpaid → opens pricing modal, logged-out → /signup) — so all pages behave identically for auth and checkout. A terse request like "update the navbar and payment button" means replacing static `href="#pricing"` anchors with this entire interactive auth/checkout flow. Confidence: 0.92
- Wants role-aware UI: menus/dropdowns must branch on the user's role so admins see admin-specific entries (e.g., Admin Dashboard → /admin, Admin Settings → /admin/settings) while riders see their own flow (Dashboard for active, Complete Checkout for unpaid, Profile & Settings → /profile) — including the entry labels, implemented once in the shared component so it applies across all funnel pages. Confidence: 0.95
- Expects modals to fit fully within the viewport — never clipped/cut off at the top or bottom edges; cap modal height to the viewport (e.g., `max-h-[calc(100dvh-2rem)]`) with pinned (non-scrolling) header/footer chrome and an internal scrollable content area when the content is tall. Confidence: 0.85
- Insists on content/testimonial authenticity on marketing pages: use only the real supplied photos matched to the correct named reviewers, with consistent dimensions, cropping, and corner radius; never use ad/stock imagery for testimonials, and only publish testimonials and performance claims that came directly from the named reviewer (e.g., remove unverified star ratings). A terse request like "update the couple page with this photo like other page" (with specific asset filenames) means swapping the real asset photos into the testimonials matched to the right reviewer names, replacing any generic shared placeholder (e.g., a single `review.jpg` reused by all reviews), with the same styling as the other pages (`rounded-2xl`, `object-cover`, `loading="lazy"`). Confidence: 0.85
- Treats marketing-copy accuracy as a compliance issue, not a style preference: disclaimers/claims must be worded exactly as supplied (e.g., "no monthly QuitTheApp platform fees" rather than "no monthly fees", "built for" rather than "trusted by", "Built From Real Transportation Experience" instead of "Satisfaction Guaranteed"), and unsupported claims (unattributed 5-star ratings, exaggerated statements like "making them easier to dominate") must be removed — even when the design says to "keep everything else". Confidence: 0.8
- Wants reuse of the project's existing UI primitives: confirmation/alert dialogs are built on the existing `AlertModal` (via a `useConfirmDialog` hook exposing `openConfirm`/`showAlert`), rather than introducing a new modal library. Confidence: 0.8
- Expects the dev environment to match the user's stated local API base URL (e.g., `http://127.0.0.1:3000/api/v1`); config edits follow the explicit `VITE_API_BASE_URL` variable and the exact endpoints/schemas from the supplied API guide. Confidence: 0.7
- Wants existing patterns to be extended rather than duplicated: new API slices extend the shared `baseApi` (reusing centralized auth headers + 401-refresh-retry) instead of creating a separate API with its own base query, and new guard hooks are placed in the `hooks/` folder. Confidence: 0.7
- Expects oversized assets (multi-MB JPGs added to `src/assets`) to be flagged and is receptive to compression before shipping. Confidence: 0.6
- Endorses the `overflow-x: clip` guard on `html`/`body` as the industry-standard fix for page-level horizontal scrollbar from stray elements (e.g., absolute dividers, `whitespace-nowrap` text, or translate offsets), so it should be applied globally rather than relying only on per-element fixes. Confidence: 0.7
- Treats page content being clipped vertically (e.g., hero section cut off at the bottom on a shorter laptop viewport) as a defect — sections should size with `min-h-[100svh]` so they grow naturally with their content and the page scrolls, rather than a fixed `h-[100svh]` with `overflow-hidden` that clips the bottom content unreachable. Confidence: 0.8
- Prefers fluid proportional scaling over breakpoint-jumping sizes for responsive UI: text, buttons, icons, padding, and gaps should scale smoothly with the viewport via `clamp()` tied to vw (e.g., `text-[clamp(0.875rem,1.6vw,1.375rem)]`, `py-[clamp(0.75rem,1.2vw,1rem)]`) so everything shrinks/grows in proportion to the screen ratio instead of snapping at sm/lg/xl/2xl — and critical interactive elements, especially CTA buttons, must never break at any width (keep their label/icon intact, using `min-w-0` and parent `flex-wrap` as safety). Confidence: 0.85
- On tablet and smaller devices, page content should be center-aligned across all sections (headlines, paragraphs, list rows, badges, review text, FAQ blocks, footer banner title/checkmarks, footer CTA buttons) via `text-center`/`justify-center` below `lg`, with `lg:text-left`/`lg:justify-start` restoring the desktop layout — a blanket rule, not a per-section choice; elements that turn `w-auto` at `sm` inside a full-width wrapper must still be centered (e.g., `flex justify-center` on the wrapper) so nothing drifts left on tablet. Confidence: 0.95
- For localized (Spanish) marketing copy, wants natural, professional native-language phrasing and sentence capitalization rather than title case (e.g., "También incluye", "Empezar mi negocio", "Lo hacemos por ti" — not capitalizing every significant word), and prefers idiomatically natural terms over literal translations (e.g., "recomendaciones" over "referidos"); official product/brand names (e.g., "Lo Hacemos por Ti" upgrade, ™ names) may keep their official capitalization. Confidence: 0.8
- Expects localized copy (Spanish is often longer than English) to be verified at mobile widths — headline wrapping, nav labels, CTA buttons, system cards, comparison boxes, FAQ columns, and the final pricing section must not overflow; treats longer localized text breaking the layout as a defect. Confidence: 0.7
- Marketing copy must not overpromise and must keep the $495 DIY included-scope vs. optional $199 "We Do It for You" assistance boundary precise everywhere: avoid absolutes (e.g., "works in any city" → "can be used in markets with an airport… results depend on local demand, competition, pricing, expenses"), avoid "free" wording that implies more than the purchase includes, and state included items consistently across sections (e.g., once hosting is included, it appears in the includes list/FAQ/pricing and is never listed as a separate expense). Confidence: 0.75
